# 角色与 Workflow 演进

状态：设计决策；模板评估与升级机制属于后续能力。

## Loom 的角色

Loom 是开发工作的组织者、执行宿主，以及项目状态和证据的保管者。程序负责派发、持久化、工作区、预算与验收；Pi 负责 Agent 推理循环和 durable 执行。命令验证由工具采集，完成状态由程序依据证据判定。

Agent 角色是可配置职责，不是固定常驻团队：Scout/Investigator 获取仓库事实和复现证据；Planner/Architect 定义契约与方案；Implementer 修改代码与测试；Reviewer 基于目标、diff 和实际验证独立审查。简单任务可以合并职责，不能因此省略必要验证。

## 选择哪些 Workflow

首版实现 `feature` 与 `debug`。`architecture`、`fill-function`、`refactor` 先定义规格，按真实需求实施。`delivery` 是共用尾段，也可以独立执行。架构决策可进入 feature；填函数若改变公共行为，应升级为 feature。具体阶段见 [Workflow 规格](WORKFLOWS.md)。

## 从 Meta 吸收的原则

薄控制层负责顺序与可靠性，专门职责负责推理；上下文隔离，知识按需加载；模板组合可复用技能，避免不断增加固定 Agent；失败尽量在局部处理，重试有上限。

不照搬固定角色数量、代码行数或文章性能结论。自然语言目标理解和开放式规划仍需要模型；程序确定性校验模型提出的计划，不宣称所有路由均可确定化。来源见 Meta 归档（本地开发记录，不随公开源码发布）。

## Revolution：可以重构流程，但要有版本和证据

演进分三层：单任务修改 `planVersion`；项目配置模板、验证和角色输入；发布新的模板版本，例如 `feature@1` 到 `feature@2`。阶段顺序可大幅调整，可靠性约束保持稳定。

后续改进流程为：Run 记录 → 重复失败与浪费分析 → 候选模板 → 历史任务与真实任务评估 → 发布 → 观察与回滚。Agent 可以提出并实现模板，不能用自己的完成自述证明模板更优。比较完成率、返工、人工接管、耗时和用量，不能只比较步骤数。

Run 固定原始 workflow 版本，新版本默认只用于新 Run。迁移必须显式执行，核对状态与副作用，并使受影响证据失效。任何版本都应保留用户改动、可追溯且可恢复；未知副作用不得盲目重放，不能虚报完成。
